프로세스와 쓰레드 개념

프로세스와 쓰레드 개념

  • 프로세스 : 현재 실행 중인 프로그램. 곧 실행 가능한 PCB를 가진 프로그램
    • 최종적으로 프로세서에 의해 수행되는 프로그램 단위
  • 프로그램은 저장된 파일 같은 수동적인 실체, 프로세스는 다음 실행할 명령어를 지정하는 프로그램 카운터를 가진 능동적인 실체
  • 프로세스의 구성 요소 : 프로그램(code), 데이터(전역변수), 스택(지역변수), PCB(프로세스 제어정보)
  • 프로세스 제어블록 (PCB)
    • PCB : 프로그램 관련 정보를 가진 자료구조. OS에게 프로세스 정보 제공
    • PCB에 들어있는 내용
      • 프로세스 상태 (보류, 실행, 준비, 대기, 정지 등의 상태)
      • 프로세스 번호 (프로세스의 고유 번호)
      • 프로그램 카운터 (프로세스가 다음에 실행할 명령어의 주소)
      • 레지스터 (누산기 인덱스 레지스터 등)
      • 계정 정보 (CPU가 사용된 시간량 등)
      • 메모리 관련 정보 (저장 위치)
      • 각종 중간값 (어디까지 했는지)

Tip) 프로세스와 스레드

-프로그램 (정적) -> 실행 -> 프로세스 (=task, 동적)

-운영체제는 프로그램을 메모리의 적당한 위치로 가져와서 작업 지시서 (PCB, TCB; process control block)을 만들음

-어떤 프로그램이 프로세스가 되었다 = 운영체제로부터 프로세스 제어 블록을 받았다는 의미

프로세스 상태와 제어

프로세스 상태와 제어

  • 프로세스 생성 : OS가 디스크 내의 프로그램을 선택해 그 프로그램의 PCB를 만들어 프로세스를 생성한다. PCB에 프로세스 이름, 우선 순위, 할당된 자원목록 등을 기록한다. 프로세스는 준비 상태가 되어 준비큐에 들어간다.
  • 프로세스 소멸 : 프로세스가 소멸될 때 PCB가 회수되고 프로세스는 제거된다. 프로세스의 프로그램 부분은 디스크에 저장되어 보관된다.
  • 프로세스 대기 : 프로세스가 자신이 하던 작업을 멈추고 대기한다.
  • 프로세스 재동작 : 대기 중인 프로세스는 기다리던 사건이 일어나면 이전 상태로 되돌아간다.
  • 프로세스 상태
    • 생성 상태 : 프로세스가 처음 생성되는 상태
    • 준비 상태 : 프로세스가 필요한 자원들을 할당받은 상태. 준비큐에서 대기 중인 상태 원본과 다름 · 원본: “대기큐에서 대기 중인 상태”
    • 실행 상태 : 프로세스가 CPU를 점유해 실행 중인 상태
    • 대기 상태 : 주기억장치에 적재는 되었지만 필요한 자원을 얻지 못한 상태
  • 상태 전이
    • dispatch : 프로세스 스케줄러에 의해 결정된 우선순위에 따라 프로세스가 CPU를 점유하게됨
    • time out : 프로세스가 실행중이다가 제한된 시간이 지나 CPU 점유를 빼앗김
    • block : 실행 중이던 프로세스가 입출력 명령을 만나면 인터럽트가 발생해 입출력 전용 프로세스에게 CPU 양도 후 자신은 대기 상태 전환
    • wake up : 프로세스가 자원을 할당받음

동기화

  • 임계 영역 문제
    • 임계 영역 (critical section) : 상호 배제를 구현하기 위해, 여러 프로세스가 함께 쓰는 자원을 참조하는 문장들의 집합 (= 공유 메모리가 참조되는 프로그램 구간)
    • 경쟁 상황 (race condition) : 동시에 여러 프로세스가 같은 자료에 접근해 조작하고, 실행 결과가 접근이 일어난 특정 순서에 따라 달라지는 상황 → 임계 영역 문제를 풀어 해결
    • 프로세스의 구조
      • 진입 구역 : 임계 영역에 들어가기 위해 허용을 요구하는 코드 영역
      • 출구 구역 : 임계 영역을 벗어나기 위한 코드 영역
      • 잔류 구역 : 프로그램의 나머지 코드 영역
  • 임계영역 해결 방법이 갖춰야 할 3가지 조건
    • 상호 배제 : 누군가 임계영역을 실행하고 있다면, 다른 프로세스들은 임계영역 진입 불가
    • 진행 : 임계영역에 진입하고 싶어서 대기하고 있는 프로세스들 중에서, 다음 임계영역 진입자 결정 가능. 이 선택은 무한 연기 불가 (누군가 계속 선택되어야 함)
    • 한정된 대기 : 임계영역에 진입하고 싶어서 대기하고 있는 프로세스는, 자기가 임계영역 진입 허락을 받기 전까지 다른 프로세스가 임계영역에 진입하는 것을 보는 횟수가 한정적이어야 함 (무한 대기 X)
    • 진입 요청부터 허용까지의 대기 시간에도 한계가 있어야 함. 그렇지 않으면 기아상태 발생
  • 임계 영역 문제를 풀 때 고려할 것
    • 상호 배제 : 임계영역 알고리즘
    • 동기화 : 다른 프로세스에게도 알려 주기 → 세마포어 (모니터)
    • 결정성 : 어떤 상황에서도 같은 값이 나와야 함
    • 교착상태 : 은행원 알고리즘
    • IPC : 프로세스 사이에 데이터를 주고받는 전달 체제
    • 병행 수행
  • 임계 영역 문제 해결 알고리즘
    • SW적 해결 기법
      • 2개 프로세스 상호 배제 : Peterson 알고리즘 / Dekker 알고리즘
      • N개 프로세스 상호 배제 : Lamport의 빵집 알고리즘 / Dijkstra 알고리즘
    • HW적 해결 기법 (동기화 하드웨어) : Test-and-Set 명령 / Burns 알고리즘 / SWAP 명령
    • 그 밖의 도구 : Mutex / Semaphore

  • Lamport의 빵집 알고리즘
    • 번호표 사용해서 임계영역 해결, 동일 번호표 인정
    • 번호표 숫자 작을수록 우선 선발
    • 프로세스들은 한계 대기 (무한 웨이팅)만 안 하면 되고, 반드시 들어온 순서대로 수행되는 것은 아님
    • 번호표가 같다면, 프로세스 number가 작은 것부터 우선 선발 → 상호 배제 O
    • 변수
      • bool choosing : true = 번호표 뽑으려고 줄 섰음. 대기 중 / false = 번호표 뽑았음
      • number[i] : 프로세스 i가 받는 번호표가 저장되는 배열
    • 상호 배제 O : while문으로 번호표 뽑으려고 대기 중인 프로세스 기다리기, 번호표 같은 경우 내가 기다리기 규칙
    • 진행 O : 임계구역 벗어나면 번호표를 0으로 만들어 다른 프로세스 방해 X
    • 한계 대기 O : 번호표 사용하기 때문
// 프로세스 Pᵢ 시점
while (1) {
  choosing[i] = true;   // 번호표 뽑으려고 줄 섰음. 대기 중
  number[i] = max (number[0], … number[n-1]) + 1;   // 나의 번호표 = 지금까지 뽑힌 번호표의 최대값 + 1
  choosing[i] = false;   // 내 상태를 번호표 뽑은 상태로 바꿈
  for (j = 0; j < n; j++) {   // 다른 프로세스와 번호표 비교 대조하는 반복문
    while ( choosing[j] );   // 다른 프로세스 중, 번호표 뽑으려고 대기 중인 애가 있으면 대기
    while ( number[j] &&
            (number[j], j) < (number[i], i) );   // 다른 프로세스 j가 번호표를 가지고 있고 && 내 번호표랑 같은데, 프로세스 번호가 더 작다면 내가 대기 (j가 들어간다)
  }
  #임계구역
  number[i] = 0;   // 사용 완료로 번호표 버리기
}
  • Lamport의 빵집 알고리즘 보충
    • 단점 : 같은 번호표가 여러 개 생길 수 있음. SW 방식이라 코드 한 줄마다 끼어들 수 있어서 원자성 보장이 필요
    • choosing[] 은 false, number[] 는 0 으로 초기화
    • (a, b) < (c, d) : a < c 이면 true, a = c 이면 b < d 일 때 true
    • while (choosing[j]); 가 필요한 까닭
      • Pj 가 번호표를 받고 있는 중이면 다 받을 때까지 기다려 준다는 뜻
      • 번호표를 받는 일도 한 순간에 한 프로세스만 해야 하는데, 위 알고리즘은 그렇지 못함
      • Px 가 번호표를 받는 중에(max 값을 확인하고 +1 하기 전에) Pi 도 번호표를 받아 for 루프로 먼저 들어가 버리면 number[i] 와 number[x] 가 같아질 수 있음 → 이런 경우를 생각해서 기다려 줌
  • HW적 해결 기법 ① Test-and-Set 명령
    • 상호 배제 O : lock 을 쓰기 때문
    • 진행 O : 빠져나온 프로세스가 lock 을 풀어 주기 때문
    • 한계 대기 X : lock 이 풀리기를 기다리는 프로세스가 여럿이면 하드웨어 속도(랜덤)에 따라 갈림 → 기아 문제가 생길 수 있음 (하드웨어 속도 차이로 인한 무한 연기)
    • 동작
      • lock 값이 true 일 때는 initial 값이 항상 true 이므로 TestAndSet 은 항상 true 를 반환 → 프로세스는 while(TestAndSet(&lock)); 루프를 빠져나가지 못함 (다른 프로세스 하나가 임계구역에 들어가 있다는 뜻)
      • 그때 기다리던 프로세스 중 가장 먼저 TestAndSet 을 실행한 프로세스가 루프에서 false 를 반환받고 while 문을 빠져나와 임계구역에 진입
      • 이 과정에서 boolean initial = lock; 과 lock = true; 는 동시에 실행되므로 다른 프로세스들은 계속 루프를 빠져나오지 못하고 대기
      • 임계구역에 들어갔던 프로세스는 빠져나오면서 lock = false; 를 수행
  • HW적 해결 기법 ② Burns 알고리즘 (Test-and-Set 개선)
    • Test-and-Set 명령을 사용해 임계 구역 문제의 모든 요구 조건을 충족하는 알고리즘 → 대기 순서에 차례를 줌 (순환 순서)
    • key, j : 지역 변수 (자기 프로세스 한정)
    • lock, waiting : 공유 변수, false 로 초기화
    • 상호 배제 O : 임계 영역에 들어가려면 waiting[i] = false 이거나 key = false 여야 함
      • 어떤 프로세스가 임계구역을 떠날 때 기다리는 다른 프로세스가 없으면 lock = false 가 되고, 그 뒤 처음 Test-and-Set 을 호출한 프로세스만 key = false 가 됨. 기다리는 다른 프로세스들이 있으면 그중 한 프로세스만 waiting[i] = false 가 됨
    • 진행 O : 대기하는 프로세스 중 waiting[j] = false 가 되는 Pj 가 임계 영역에 들어감
    • 한계 대기 O : 순환 순서로 대기 중인 프로세스를 검사하므로 i 다음 순서부터 차례로 순서가 돌아옴 (최대로 기다려도 n − 1)

교착상태

  • 교착상태 한눈에 보기
  • 교착상태의 필요조건 (발생조건)
    • 네 가지 조건이 동시에 성립될 때 발생
    • ① 상호배제 (mutual exclusion)
    • ② 점유와 대기 (hold and wait) : 자신에게 할당된 자원이 있으면서 다른 자원의 할당을 대기 원본과 다름 · 원본: “wait-for”, 이 조건의 영어 이름은 hold and wait
    • ③ 비선점 (no preemption) : 어떤 프로세스에 할당된 자원을 빼앗을 수 없음
    • ④ 환형대기 (circular wait) : 프로세스가 closed chain 을 이루고 있으면서 각 프로세스가 체인의 다음 프로세스가 필요로 하는 자원을 최소 하나씩 갖고 있는 상태
      • 환형대기는 점유와 대기를 암시하므로 완전 독립적인 조건은 아니지만 구분함
  • 교착상태 예방 방법
    • 조건 중에서 최소한 하나가 성립하지 않도록 보장함으로써 교착상태 예방
    • ① 상호배제 : 모든 자원을 공유 가능하도록 함
      • 단점 : 현실적으로 공유 불가능한 자원이 있음 (ex. 프린터)
    • ② 점유와 대기
      • i) 각 프로세스가 실행되기 전에 자신의 모든 자원을 요청하고 미리 할당받을 것
      • ii) 프로세스가 자원을 전혀 갖고 있지 않을 때만 자원을 요청할 수 있음 (요청하려면 갖고 있던 자원을 모두 반납해야 함)
      • 단점 : 자원의 이용도가 낮아짐, 기아 상태 가능 (인기 많은 자원을 필요로 하는 프로세스는 무한정 대기해야 할 수 있음)
    • ③ 비선점 : 선점 허용
      • 어떤 자원을 점유 중인 프로세스가 즉시 할당할 수 없는 다른 자원을 요청하면 갖고 있던 자원을 뺏김
      • 프로세스가 요청 중인 새로운 자원을 할당받고, 대기 중에 선점되었던 모든 자원을 회복할 때만 다시 시작 가능
      • 단점 : 선점에 따른 동기화 알고리즘이나 오버헤드 증가
    • ④ 환형대기 : 모든 자원 타입에 전체적인 순서를 부여하여, 각 프로세스가 열거된 순서대로 오름차순으로 자원을 요청하도록 요구
      • 단점 : 새로운 자원 추가 시 현존 프로그램, 시스템 재구성
    • 예방의 문제점 : 장치의 이용률이 저하되고 시스템 처리율이 감소됨
  • 교착상태 회피
    • 자원이 어떻게 요청될지에 대한 추가 정보를 제공하도록 요구
    • 자원 상태 정보를 이용하여 안전 상태를 유지하도록 능동적으로 조정하는 방법
    • 프로세스들이 자원을 요청하면 시스템은 그것을 바로 들어줄지, 기다리게 할지를 결정
    • 자원 할당 상태 (State) : 사용 가능한 자원 / 할당한 자원 / 프로세스 자원 요구의 최대 값
    • 안전 상태 (Safe State) : 모든 프로세스들이 교착상태를 일으키지 않으면서 수행을 끝낼 수 있는 순서가 최소 하나 이상 존재
      • 안전 : OS 가 프로세스에게 자원을 할당해도 교착상태에 빠지지 않는다
      • 시스템이 안전 순서를 찾을 수 있는 상태
    • 불안전 상태 (Unsafe State) : 교착상태가 발생할 수 있는 상태 (불안전하다고 반드시 교착상태가 발생하는 것 X)
      • 시스템이 안전 순서를 찾을 수 없는 상태
    • 안전 순서 (Safe sequence) : 모든 프로세스들의 종료 순서
    • 회피의 문제점
      • ① 프로세스가 수행을 위해 필요한 자원을 모두 파악하는 것이 어려움
      • ② 자원 이용률은 회피를 쓰지 않을 때에 비해 낮아짐
      • ③ 프로세스의 실행 순서가 우선순위나 동기화에 의해 수행 순서의 제한을 받지 않아야 함 (가용 자원이 할당 가능하면 프로세스 수행을 시작해야 해서 프로세스 스케줄링 정책과 충돌 발생)
      • ④ 어떤 프로세스도 자원을 보유한 상태로 exit 될 수 없어야 함
      • → 회피 전략은 교착상태 가능성을 예측할 뿐
    • 회피 알고리즘 : 자원 할당 그래프 알고리즘 (인스턴스 하나), 은행원 알고리즘 (인스턴스 여러 개) → 3.2.8
  • 교착상태 탐지
    • 주기적으로 환형대기 발생했는지 탐지 → 발생 시 해결
    • 자원 할당이 가능하다면 항상 자원을 할당해줌
    • 교착상태가 발생하면 회복 작업 수행
    • 해결법 : 자원할당그래프 소거법, 개선된 은행원 알고리즘
    • 회피 vs 탐지
      • ① 교착상태에 빠질 수 있는지 미리 예측하는 부분이 탐지 알고리즘에는 존재 X
      • ② 각 프로세스는 시작할 때 운영체제에게 자신이 요구할 자원의 최대량을 미리 알릴 필요 X (Max 필요 없음)
  • 자원할당 그래프
    • 요청 간선 Pi → Rj : 프로세스 Pi가 자원 Rj에서 1개의 자원을 요청하고 대기
    • 할당 간선 Rj → Pi : 자원 Rj의 자원 1개가 프로세스 Pi에 할당됨 원본과 다름 · 원본: “프로세스 Pi가 자원 Rj에서 1개의 자원을 요청했었고 대기”
    • if 순환 사이클이 없다 = 교착상태 없다
    • if 순환 사이클이 있다
      • 순환에 참여한 모든 자원이 하나의 instance만 가지고 있다 = 반드시 교착상태
      • 순환에 참여한 자원이 여러 개의 instance를 가지고 있다 = 반드시 교착상태 X
    • 소거법
      • 자원할당 그래프를 이용해서 교착상태 탐지하는 방법
      • 그래프의 간선이 모두 제거된다면 교착상태 X
      • 그래프의 간선이 모두 제거되지 못하면 교착상태 존재 탐지 O
    • 소거법 순서
      • ① (자원 입장에서) unblocked P 찾아서 선택 (당장 자원할당 해줄 수 있는 프로세스 찾기)
      • ② 선택한 unblocked P와 관련된 edge 제거 (=종료되었다고 간주)
      • ③ 반복
  • 대기 그래프 알고리즘
    • 자원 타입마다 인스턴스가 하나만 존재하는 경우
    • 대기 간선 사용 (대기 간선 Pi → Pj는 프로세스 Pi가 Pj가 가진 자원을 기다리는 것) 원본과 다름 · 원본: “대기 간선 Pi → Rj는 프로세스 Pi가 자원 Rj 기다리는 것”
    • 사이클 탐지 알고리즘 이용해 검사
  • 개선된 은행원 알고리즘
    • 자원 타입마다 인스턴스가 여러 개 존재하는 경우 (m × n²)
    • 프로세스의 자원 할당 → 요청 항상 할당 (주어진 상태에서 교착상태 여부 찾기)
    • 프로세스는 존재하지만 아직 자원을 할당받기 전인 프로세스 (Allocation = 0)는 어차피 교착상태와 상관 X → 처음부터 Finish[i] = true
    • 안전 알고리즘과 다른 점 : 처음에 Allocation[i] ≠ 0 인 프로세스만 Finish[i] = false, Need[i] 대신 Request[i] ≤ Work 로 찾음
    • 예 : P0 ~ P4 프로세스 / 자원 A(7), B(2), C(6)
      • work = (0, 0, 0) 에서 Request ≤ work 인 프로세스를 P0 → P2 → P1 → P3 → P4 순으로 끝낼 수 있어 모든 Finish[i] = true → 교착상태 아님
  • 교착상태 회복
    • 교착상태 회복 : 사이클이 없어질 때까지 프로세스 종료시킴 or 할당된 자원 중단시킴
    • (1) 교착상태 프로세스 모두 종료시킴
      • 장점 : 확실하게 교착상태 사이클 없앨 수 있다
      • 단점 : 비용이 크다 (프로세스가 연산한 결과 다 버려야함)
    • (2) 교착상태 제거될 때까지 한 프로세스씩 종료
      • 단점 : 오버헤드 크다 (프로세스가 종료될 때마다 탐지 알고리즘 호출해서 프로세스들이 아직도 교착상태인지 확인해야함)
    • (3) 교착상태 프로세스들로부터 자원을 선점함
      • 자원 선점 시 고려사항
        • ① 희생자 선택 : 비용 최소화하는 방향으로 자원 선점 순서 결정해야함
        • ② 복귀 (rollback) : 시스템이 실행하는 모든 프로세스들의 상태 정보 유지해야함 원본과 다름 · 원본: “복귀 (rollover)”
        • 복귀 방법 : 프로세스를 안전한 상태로 후퇴시키고, 그 상태부터 재시작
        • ③ 기아 : 기아상태 발생하면 안됨
        • 기아 방지 : 동일 프로세스가 계속 희생될 수 있으므로 비용 요소에 후퇴(rollback) 횟수를 포함시킴

프로세스 스케줄링

  • 스케줄링의 개념
    • 작업을 처리하기 위해 프로세스들에게 중앙 처리 장치나 각종 처리기들을 할당하기 위한 정책을 계획하는 것
    • 스케줄링의 기준 : CPU이용률, 시스템 처리율 최대화, 반환시간, 대기시간, 응답시간 최소화 되어야함
      • CPU이용률 (CPU utilization) : 프로세스들이 CPU를 사용하는 비율
      • 시스템 처리율 (throughput) : 단위 시간당 완료한 프로세스 개수 (= 처리한 프로세스 개수)
      • 반환시간 (turnaround time) : 프로세스가 제출된 때부터 실행을 마칠 때까지 걸린 시간 원본과 다름 · 원본: “프로세스들이 준비큐에서 대기하는 시간”
        • = 총 처리시간. 메모리에 들어가기 위해 기다린 시간, 준비큐에서 대기하는 시간 등을 모두 포함
      • 대기시간 (waiting time) : 프로세스들이 준비큐에서 대기하는 시간 원본과 다름 · 원본의 반환시간 설명을 이 줄로 옮김
        • 큐의 길이에 의해 측정될 수 있음
      • 응답시간 (response time) : 프로세스가 요구한 시간부터 첫 번째 응답이 나올 때까지의 시간 (= 반응시간)
  • MTBF · MTTF · MTTR
  • 스케줄링 기본요소
    • CPU burst cycle vs I/O burst cycle
      • 프로세스의 실행은 CPU 실행과 입출력 대기 사이클로 구성됨
      • CPU 버스트 → 입출력 버스트 → … 교대로 발생
    • CPU 중심 job vs I/O 중심 job
      • CPU 중심 프로그램은 긴 CPU 버스트를 가짐
        • 연산을 위해 많은 명령어를 수행
      • I/O 중심 프로그램은 짧은 CPU 버스트, 입출력을 위해 많은 시간을 대기
    • CPU 스케줄러 : CPU가 쉬고 있을 때 운영체제가 다음에 실행할 프로세스를 준비큐에서 선택하는 과정. 실행준비가 된 프로세스를 선택하고 CPU를 할당
      • 단기 스케줄러가 맡음
    • 문맥 교환 (Context switch) : CPU가 한 프로세스에서 다른 프로세스로 전환할 때, 실행하던 프로세스 상태를 보관하고 새로운 프로세스 정보를 적재해 실행 준비하는 것
  • 스케줄링 큐
    • 프로세스는 준비큐에서 CPU를 할당받은 후 실행 상태가 됨
    • 프로세스가 실행 중일 때 I/O 요청이 들어오면 대기 상태가 되고, I/O queue에서 대기
    • 실행 중에 인터럽트 발생 시, 준비 상태가 되어 준비큐에서 CPU 할당을 기다림
    • 작업 큐 (job queue) : 주기억장치의 할당을 기다리며 대용량의 기억장치에 있는 프로세스들로 구성됨
      • 아직 프로세스로 활성화되지 않은 상태
    • 준비 큐 (ready queue) : 주기억장치에 적재되어 있으면서 CPU에 의해 실행되기를 준비하는 프로세스들로 구성됨
    • 장치 큐 (device queue) : 특정 입출력 장치를 기다리고 있는 프로세스들로 구성됨
  • 프로세스 스케줄링 (CPU 자원할당) 유형별 분류
    • 기능별 분류
      • 장기 스케줄러 : 어떤 프로세스를 준비큐에 넣을 것인가? (= 작업 스케줄러)
        • 호출을 가끔 하기 때문에 장기 스케줄러
        • 새로운 프로세스가 생성되었을 때, 현재 활동 중인 프로세스 모임에 새로운 프로세스를 추가하는 역할
        • 풀에서 프로세스들을 선택해 실행하기 위해 메모리로 적재
        • 다중 프로그래밍 정도를 결정 (동시에 올라가 있는 프로세스 수 조절)
      • 중기 스케줄러 : 메모리에 적재된 프로세스 수 관리
        • 너무 많은 프로세스에게 메모리를 할당해 시스템 성능 저하 시, 적재된 프로세스 수 조절 (swap out 시킴)
        • 메모리에서 CPU를 경쟁하는 일부 프로세스를 제거해 다중 프로그래밍 정도를 완화
        • 차후에 제거되었던 프로세스를 다시 메모리로 불러와 중단되었던 지점부터 실행 재개 (swap in)
      • 단기 스케줄러 : 어떤 프로세스에게 CPU를 할당할 것인가? (= cpu 스케줄러)
        • 준비 상태의 프로세스 중에서 어떤 프로세스를 다음에 실행 상태로 만들 것인지 결정
        • CPU를 위해 반드시 자주 새로운 프로세스를 선택해야 함
    • 방법별 분류
      • 선점 (preemptive) 방식 : 실행 중인 프로세스보다 높은 우선 순위의 프로세스가 있으면, 현재 실행 중인 프로세스를 중지시키고 실행한다
        • 종류 : RR, SRT, MLQ, MFQ
        • 높은 우선순위 프로세스에게 빠른 반응시간 제공
        • 실시간 시스템, 대화식 시분할 시스템에 적합
        • 단점 : 오버헤드 발생 (수행 프로세스를 중지시키고, 수행한 내용이 제거됨)
      • 비선점 (Non-preemptive) 방식 : 수행 프로세스를 중지하고 다른 프로세스를 수행시킬 수 없는 스케줄링 방법
        • 종류 : FIFO, SJF, HRN
        • 응답시간 예측이 용이
        • 단점 : 호송효과 (호위효과) – 많은 프로세스들이 하나의 긴 프로세스 때문에 대기

    • ④ 프로세스가 대기 → 준비완료 상태로 전환될 때 (ex. 입출력 종료 시) : 선점

3.2.6

CPU 스케줄링 알고리즘

CPU 스케줄링 알고리즘

  • 알고리즘별 분류
    • 우선순위, 기한부, FIFO, 라운드 로빈, SJF, SRT, HRN, MLQ, MFQ
  • FIFO (First In First Out) : 비선점
    • FIFO = FCFS. 도착순서대로 CPU 할당
    • 긴 작업에게 유리, 짧은 작업에게 불리
    • 장점 : 간단한 코드, 공정성 제공, 선입선출 큐를 이용해 쉽게 관리 가능
    • 단점 : 호송효과 (호위효과) 발생 – 짧은 프로세스들에게 불리
      • 대화식 시스템, 시분할 시스템에 부적합
      • CPU 이용률이 떨어짐, 평균 대기시간 ↑
  • SJF (Shortest Job First) : 비선점
    • 처리해야 할 실행 시간이 가장 작은 프로세스에게 CPU 할당
      • 실행 시간 = 프로세스 전체 길이가 아니라 다음 CPU burst 길이가 기준
      • 실행 시간이 같으면 FCFS 적용
    • 짧은 작업에게 유리
    • 기아현상 발생 → 긴 프로세스는 자기 차례 기다리다가 굶어죽게 됨
    • 장점 : 최소 평균 대기시간
    • 단점 : 작업 실행 시간 (CPU 요청의 길이) 예측이 어려움 → 장기 스케줄링에서 주로 사용 (단기 스케줄링은 다음 CPU burst 길이를 알 수 없음)
    • 시분할 시스템, 트랜잭션 시스템에 부적합
  • HRN (Highest Response Ratio Next) : 비선점
    • 긴 작업과 짧은 작업의 불평등을 보완한 기법. 대기 중인 프로세스의 대기 시간, 실행 시간 고려 → α값 큰 순서대로 선택
    • 기아현상 해결 → aging 기법 (경로 우대)
    • α값이 크다 = 대기시간
  • SRT (Shortest Remaining Time) : 선점
    • SJF (실행시간 가장 짧은 것) + 선점
    • 완료되기까지의 실행 시간 추정치가 가장 작은 프로세스에게 CPU 할당
    • 단점 : 오버헤드, 기아현상 발생할 수 있음
  • RR (Round Robin) : 선점
    • 큐에 먼저 들어온 프로세스가 먼저 CPU 할당받음 + timeslice동안만 실행 후, 완료되지 않았으면 준비큐 맨 뒤로 이동
      • 각 프로세스는 시간 할당량만큼 CPU 점유, 클록 인터럽트 발생 시 레디큐로 이동
      • 원형 큐 사용 – FCFS 방식으로 다음 큐가 실행됨
    • 순서 + timeslice 선점
    • timeslice
      • 시간 할당량 (타임 퀀텀)은 문맥교환의 효과를 고려해 정함 (성능 좌우)
      • 크다 : FIFO와 동일해짐
      • 작다 : 선점 횟수 많아짐 → 오버헤드 증가
    • 단점 : 선점 발생, 선점 횟수 많아짐
    • 선점 최적화 방법 → 멀티큐 (다중큐)
    • 대화식 시분할 시스템에 적합
  • 우선순위 스케줄링 : 선점형 / 비선점형 둘 다 가능
    • 정적 우선순위 : 실행이 쉽고 오버헤드 적음 / 주위 여건 적응 X, 우선순위 바뀌지 X
    • 동적 우선순위 : 상황 변화에 잘 적응 / 구현 복잡, 오버헤드 큼
    • 내부적 우선순위 : 시간 제한, 메모리 요구, 열린 파일의 수, 평균 입출력 버스트의 평균 CPU 버스트에 대한 비율 등
    • 외부적 우선순위 : 프로세스의 중요성, 컴퓨터 사용을 위해 지불되는 비용의 타입과 양, 그 작업을 후원하는 부서 등
    • 단점 : 무한 봉쇄, 기아 → 노화 (aging) 사용
  • MLQ (Multi-Level Queue, 다단계 큐 스케줄링) : 선점 (우선순위 큐에 따른 선점)
    • 작업을 여러 종류의 그룹으로 나누어 각 큐의 독자적 스케줄링에 따라 CPU 할당 (고정 할당, 큐 간 이동 없음)
    • 큐들 간에 작업 이동 불가능 (큐를 처음부터 우선순위로 정렬해야 함 – 트리로 구현하기도 함)
    • 장점 : 스케줄링 오버헤드 ↓
    • 단점 : 융통성 없음
    • 우선순위 낮은 프로세스들은 계속 밀려나게 됨 → MFQ
  • MFQ (Multi-level Feedback Queue)
    • 다단계 피드백 큐에서 우선순위 높은 큐에 대기 중인 프로세스가 존재한다면, 무조건 그 큐가 먼저 CPU를 점유하고 그 큐를 진행하러 감
    • 다단계 귀환 스케줄링, 선점 – 선점의 최소화 (최적 선점이 목적)
    • 입출력 위주와 CPU 위주인 프로세스의 특성에 따라 서로 다른 time slice 부여
    • 주어진 시간 할당량이 완료되면 다음 단계의 큐에 배치 (큐 간 이동 허용, aging)
    • 프로세스의 실행시간이 길수록 점점 낮은 순위를 지니게 됨, 가장 낮은 우선순위 큐에 도달하면 순환 할당 (RR) 방식으로 스케줄링
    • RR에 비해 MFQ의 장점 : 선점 횟수 최소화
      • 6초짜리 작업이면 2초씩 3번 (2×3) 나누는 것보다, 2×1 다음 큐에서 4×1 로 하는 것이 선점 횟수가 더 적음
    • 큐마다 정책, 알고리즘, 퀀텀이 다 다름
    • 매개변수
      • ① 큐의 개수
      • ② 각 큐를 위한 스케줄링 알고리즘
      • ③ 한 프로세스를 높은 우선순위 큐로 올려 주는 시기 결정 방법
      • ④ 한 프로세스를 낮은 우선순위 큐로 강등시키는 시기 결정 방법
      • ⑤ 프로세스가 서비스를 필요로 할 때 프로세스가 들어갈 큐 결정 방법

임계영역 알고리즘과 세마포어의 사례

  • 세마포어 (semaphore)
    • 상호 배제를 해결하기 위한 동기화 도구
      • 임계영역에 들어가기 전에 스위치를 '사용 중'으로 놓고 들어가므로, 다른 알고리즘처럼 임계영역이 잠겼는지 검사하거나 바쁜 대기하거나 다른 프로세스에 동기화 메시지를 보낼 필요가 없음
    • 세마포어 변수 : 정수 변수. 초기화 연산과 표준 연산 wait(), signal() 로만 접근할 수 있음
    • wait(s) = P(s) : S 를 줄임 (−)
    • signal(s) = V(s) : S 를 늘림 (+)

  • 세마포어 변수의 유형
    • 이진 세마포어 (binary semaphore) : 공중전화 박스
      • mutex lock 과 비슷하게 동작
      • S = 1 : 임계영역 사용 가능 / S = 0 : 임계영역 사용 중
      • wait(s) : S 가 1 이 되면 0 으로 바꾸며 들어감 / signal(s) : 나올 때 기다리던 프로세스를 들여보내거나 S = 1 로 함
    • 카운팅 세마포어 (counting semaphore, 범용 세마포어) : 주차장
      • 가용 자원의 개수로 초기화
      • n 대 주차할 수 있는 주차장 (n : 정수형 세마포어, 주차장 : 공유 자원)
      • n > 0 : 주차장(공유 자원)으로 들어가면서 n − 1 / n = 0 : n > 0 이 될 때까지 대기 / (n < 0 : 공유 자원을 기다리는 프로세스 수)
      • wait(s) : 주차장에 빈 곳을 기다렸다가 빈 곳이 생기면 S − 1 하고 진입 / signal(s) : 주차장에서 나올 때 기다리던 차 입장 (S + 1)
  • 바쁜 대기와 대기 리스트
    • 바쁜 대기 (busy waiting) : 어떤 프로세스가 임계영역 안에 있는 동안, 기다리는 다른 프로세스들이 진입 코드에서 계속 무한 루프를 도는 현상 (CPU 시간 낭비)
    • block / wake up : CPU 스케줄러를 이용해 프로세스를 block / wake up 해서 바쁜 대기를 없앰
      • wait, signal 연산을 고치고, 세마포어 정의에 프로세스 대기 리스트(process waiting list)를 추가
      • 세마포어가 음수일 때, 그 절댓값은 세마포어를 기다리는 프로세스 수
      • 같은 세마포어에 대해 두 프로세스가 동시에 wait(), signal() 을 할 수 없음 (원자성이 반드시 보장되어야 함)
  • 고전적인 동기화 문제 ① 생산자 & 소비자 문제
    • 카운팅 세마포어 사용
    • semaphore mutex = 1 : 버퍼 접근 상호 배제용 (Boolean 변수, 이진 세마포어)
    • semaphore empty = n : 빈 방 개수 (카운팅 세마포어)
    • semaphore full = 0 : 데이터 개수 (카운팅 세마포어)
  • 2008 기출 - 모니터
    • 원래 모니터에는 mutex 를 쓰지 않음 → 오류가 있는 문제
  • 고전적인 동기화 문제 ② 읽기-쓰기 문제
    • 자료 객체(파일, 레코드)는 여러 프로세스 사이에서 공유
    • reader(판독자), writer(기록자)가 있음
    • 판독(reading)은 동시에 할 수 있음 / 기록(writing)은 상호 배제가 필요
    • semaphore rw_mutex (= wrt) = 1 : R, W 모두 공유. W 에 대한 상호 배제 (R&W, W&W 모두)
    • semaphore mutex = 1 : read_count 상호 배제를 위해 사용
    • int read_count = 0 : 몇 개의 프로세스가 읽고 있는가 (R 개수)
    • Q. 읽기 프로세스 두 개가 들어왔는데 쓰기가 실행 중이면? : R1 은 wait(wrt) 에서 기다리고, R2 는 wait(mutex) 에서 기다림
    • 쓰기 프로세스의 기아 상태가 생길 수 있음 (읽기 프로세스에게 새치기당해서)
    • 예제 (1) : 읽기 프로세스가 6 을 수행하고 있는 동안 쓰기1 → 읽기2 → 읽기3 의 요구가 들어옴 (읽기3 은 읽기2 가 3 을 수행할 때 시작, 읽기2 는 읽기3 이 6 을 수행할 때 읽기 영역을 빠져나감)
    • 예제 (2) : 쓰기1 프로세스가 b 를 수행하고 있는 동안 읽기1 → 쓰기2 → 읽기2 요구가 들어온다면, 이를 처리할 때 wrt 대기 리스트에 들어가는 프로세스를 순서대로 나열하시오.
  • 고전적인 동기화 문제 ③ 식사하는 철학자 문제
    • 포크 2 개를 이용해 식사하고, 식사가 끝나면 포크를 내려놓고 thinking
    • 포크를 세마포어를 이용해 공유 자원(배열)으로 정의하고, 모든 원소를 1 로 초기화
    • wait 명령으로 포크를 잡고, signal 명령으로 포크를 제자리에 둠
Program DiningPhilosophers
  var fork: array[0, 1, 2, 3, 4] of semaphore(=1); n: integer
  procedure philosopher(i: integer);
do {
  wait(fork[i]);            //포크 0번 잡고
  wait(fork[(i+1) % 5]);    //포크 1번 잡고
  //eat
  signal(fork[i]);          //포크 0번 놓고
  signal(fork[(i+1) % 5]);  //포크 1번 놓고 (내려놓는 순서 상관없음)
  //think
} while (true);
  • 알고리즘의 문제점 : 5 명의 철학자가 동시에 식사하면 모두 왼쪽 포크만 가지게 되고(왼쪽부터 잡음), 이미 다른 철학자가 가진 오른쪽 포크를 기다리는 교착상태가 생김 → 기아 현상 초래
  • 교착상태 방지법
    • ① 동시성 제어 : 한 번에 최대 4 명의 철학자만 테이블에 동시에 앉을 수 있게 함 (room 변수를 넣어 4 로 인원 제한)
    • ② 한 철학자가 포크 두 개를 모두 집을 수 있을 때만 포크를 집게 함 (임계영역 안에서만 포크를 집어야 함)
    • ③ 비대칭 해결안 : 홀수 번호 철학자는 L → R 순으로, 짝수 번호 철학자는 R → L 순으로 집게 함
    • ④ 순환 끊기 : 마지막 철학자만 R → L 순으로 집게 함
3.2.8

교착상태(deadlock)와 은행원 알고리즘

  • └교착상태 원리와 발생 조건, 해결방안 (예방/회피/발견 및 회복)

교착상태(deadlock)와 은행원 알고리즘

  • 자원 할당 그래프 알고리즘
    • 자원 타입마다 인스턴스가 하나만 존재하는 경우
    • 예약 간선 : Pi → Rj 는 Pi 가 미래에 자원 Rj 를 요청할 것이라는 의미, 점선으로 표시
    • 사이클 탐지 알고리즘을 이용하여 검사
  • 은행원 알고리즘
    • 자원 타입마다 인스턴스가 여러 개 존재하는 경우
    • 프로세스는 시작할 때 작업 수행을 위해 요구되는 자원의 최대 값을 신고
    • 최대 값은 시스템이 보유한 자원의 총합을 넘지 않아야 함
    • 프로세스가 자원들을 요청하면 시스템은 그것을 들어주었을 때 시스템이 계속 안전 상태에 머무르게 되는지 여부를 판단
      • 그렇지 않다면 이 프로세스의 요청은 허락이 안 된 채 다른 프로세스가 끝나기까지 기다리게 됨
  • 은행원 알고리즘 자료구조 (M : 프로세스의 수, N : 자원의 종류 수)
배열 이름배열 요소쓰는 알고리즘
Available (가용 자원)해당 자원의 가용한 인스턴스 개수 (길이 = N) 원본과 다름 · 원본: “길이 = M”, 자원 종류마다 하나씩이므로 N
현재 시스템이 보유한 가용한 자원		회피, 탐지
Max (최대 자원)해당 프로세스가 필요로 하는 해당 자원의 인스턴스 개수 (길이 = M × N / 행렬)
프로세스가 시작하기 전에 운영체제에게 알리는, 자신이 요구하는 자원의 최대 값		회피
Allocation (할당 자원)해당 프로세스에게 이미 할당한 해당 자원의 인스턴스 개수 (길이 = M × N / 행렬)
운영체제가 프로세스에게 할당한 자원		회피, 탐지
Need (요구 자원)해당 프로세스가 필요로 하는 해당 자원의 인스턴스 개수 (길이 = M × N / 행렬)
프로세스가 작업을 완수하기 위해 앞으로 운영체제에게 요구할 자원의 수		회피
Request (요청 자원)해당 프로세스가 요청한 해당 자원의 인스턴스 개수 (길이 = M × N / 행렬)
주어진 시점에 프로세스가 운영체제에게 요청한 자원의 수		회피, 탐지
  • ① 자원 요청 알고리즘 : 한 프로세스의 자원 요청 시 할당이 가능한지 알아보는 알고리즘
    • 운영체제는 프로세스 Pi 의 자원 할당 요청 Request[i] 를 받는다 (Request[i, j] == k : Pi 가 Rj 를 k 개까지 요청하고 있음)
    • 모든 자원에 대해 가상으로 할당해 보기
Available     = Available     - Request[i]
Allocation[i] = Allocation[i] + Request[i]
Need[i]       = Need[i]       - Request[i]
  • ② 안전 알고리즘 : 시스템의 상태가 안전 상태인지 불안전 상태인지를 확인하는 알고리즘 (m × n²)
    • finish[ ] : 요소가 boolean 이고 길이 n 인 일차원 배열
    • work[ ] : 요소가 정수이고 길이 m 인 일차원 배열, 처음 값 : work = Available 원본과 다름 · 원본: “최대값”, 순서도처럼 처음에 Available 로 놓는 값
  • 은행원 알고리즘 예 : P0 ~ P4 프로세스 / 자원 A(10), B(5), C(7)
    • t0 : 처음 상태 (Need = Max − Allocation). 안전 순서 <P3, P1, P4, P2, P0> (또는 <P1, P3, P0, P2, P4>) 가 있어 안전 상태
    • t1 : Request1 = (1, 0, 2) 원본과 다름 · 원본: 그림의 P4 Need “4 1 1”, Max 433 − Allocation 002 = 4 3 1
      • ① Request1 ≤ Need1 (O) ② Request1 ≤ Available : (1, 0, 2) ≤ (3, 3, 2) (O)
      • 가상으로 할당 → Available (2, 3, 0), Allocation1 (3, 0, 2), Need1 (0, 2, 0) → 안전 순서 <P1, P3, P0, P2, P4> 가 있어 요청 승인
    • t2 : Request4 = (3, 3, 0) 원본과 다름 · 원본: 그림의 P4 Allocation “0 2 2”, t1 그대로 0 0 2
      • ① Request4 ≤ Need4 (O) ② Request4 ≤ Available : (3, 3, 0) > (2, 3, 0) (X) → 대기
